Same bits, different meaning

IT 520, September 28. One-page reading.

A field that runs out of room

On September 23 the tote report's count field was four bits wide, and 1101 read as 13 using place values 8, 4, 2, 1. Four bits give 24 = 16 patterns, so an unsigned four-bit field holds 0 through 15. After the sixteenth scan, 1111 + 0001 produces five bits, 1 0000. The field keeps only four, so it reports 0000. The count wrapped. A result that falls outside the range of the chosen width and rule is called overflow. (This is a teaching counter. Python integers do not wrap this way, and languages and machines differ in how they handle overflow.)

One pattern, two rules

A new four-bit "last change" field reports the net change in the count since the last report, so it needs negative values. Under the unsigned rule, 1111 is 15. Under two's complement, the same 1111 is −1. The bits did not change; the rule for reading them did.

Two's complement does not create more patterns. It spends half of them on negative values. To read a two's complement pattern whose first bit is 1, take its unsigned value and subtract 2width: 1111 is 15 − 16 = −1; 1000 is 8 − 16 = −8. With eight bits, 1111 1111 is 255 unsigned and 255 − 256 = −1 in two's complement. The ranges are 0 through 255 and −128 through 127.

Signed fields overflow too

In four signed bits, 0111 + 0001 = 1000. That is +7 + 1, but 1000 reads as −8. The true result, +8, is outside −8 through +7, so the operation overflowed. The same bit addition 1111 + 1 overflows under the unsigned rule (15 + 1) and is correct under two's complement (−1 + 1 = 0). Overflow depends on the width and rule, not on the bits alone.

Diagnosing a strange number

  1. What is the field's width and reading rule, and do sender and reader agree on them?
  2. Does the intended value or result fit that rule's range?

If sender and reader use different rules, the fix is agreement: widening the field does not help. If the value does not fit, the fix is a wider field (or a limit on the values allowed).
