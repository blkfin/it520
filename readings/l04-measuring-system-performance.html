Measuring system performance

What this is about

Every computer system does work for someone: a web server answers requests, a database runs queries, a print room prints jobs. Computer system performance analysis is the study of how well a system does that work: how long a request takes, how much work gets finished, and how busy each part of the system is. The questions it answers come up across a system's whole life: when it is designed, when someone decides how large a system to buy, and when its workload grows.

Analysts answer those questions in three ways. They can rely on experience and intuition, which is quick but hard to verify. They can run experiments, which are accurate but expensive and describe only the conditions tested. Or they can build a model, a simplified description that keeps only what matters for the system's behavior.

You may also hear the term performance monitoring. Monitoring is one activity within this field: collecting measurements from a running system over time. It uses the same measurements introduced here.

Every one of these approaches rests on the same foundation, which is the subject of this reading: a small set of measurements with precise meanings, and two relationships that follow directly from them. With those, "the system is slow" becomes a claim you can check.

What does “fast” mean?

A system can feel slow in more than one way. One student may wait a long time for a print job, while the print room still finishes many jobs each hour. To describe performance clearly, we have to say what work we observed, where the system begins and ends, and which measurement we mean.

One print room, four measurements

Suppose we watch one printer in a campus print room across several comparable 60-minute intervals. The records show that, in an average hour:

  • 8 print jobs finish;
  • the printer is actively printing for 40 minutes; and
  • an average of 2 jobs are inside our boundary, either waiting or printing.

We will treat one submitted print job as one request. Our system boundary starts when a job joins this printer's line and ends when its pages finish. Changing either choice would change what our measurements mean.

Throughput asks how fast completed work leaves the system. If C jobs complete during an observation interval T, then

X = C / T = 8 jobs / 1 hour = 8 jobs/hour.

Throughput is a rate for many completed jobs. It does not tell us how long any one job spent in the system. It is also an observed rate, not the printer's advertised maximum speed.

Service time asks how long one request holds the resource that performs the work. The printer was busy for B = 40 minutes and finished C = 8 jobs, so each completed job used the printer for an average of

S = B / C = 40 minutes / 8 jobs = 5 minutes/job.

Service time does not include time in line. A job can require only 5 minutes of printing and still take much longer from submission to completion.

Utilization is the share of the observation interval during which a resource is busy. The printer was busy for 40 of 60 minutes, so

U = 40 / 60 = 2/3, or about 67%.

The same result follows from the Utilization Law:

U = X · S = (8 jobs/hour)(5 minutes/job) = 40 minutes/hour = 2/3.

The units matter: jobs cancel, leaving busy time divided by observed time. Utilization is not throughput. Throughput counts finished jobs per hour; utilization reports the fraction of the hour for which this printer was busy.

Latency asks how long one request spends inside the chosen system boundary, from arrival to departure. It includes both waiting and service. We could time every job directly, but the average number of jobs inside gives us another way. The relationship called Little's Law is

N = X · R,

where N is the average number of requests inside, X is throughput, and R is average latency. In the print room, N = 2 jobs and X = 8 jobs/hour, so

R = N / X = 2 jobs / (8 jobs/hour) = 0.25 hour = 15 minutes/job.

The average job therefore spends 15 minutes inside: 5 minutes receiving service and 10 minutes waiting. The two laws agree: of the 2 jobs inside on average, X · S = 2/3 of a job is printing and the other 4/3 are waiting. These are averages across the stated workload and hour, not promises about every individual job.

Why latency is not 1 / throughput

The printer completes 8 jobs per hour, so completions are spaced 7.5 minutes apart on average. That spacing is not the same as a job's 15-minute latency. Little's Law shows why: R = N / X, so latency equals 1 / X only when an average of exactly one job is inside. Here 2 jobs are inside, because while one job prints another is already waiting, so latency is twice the spacing. In larger systems, several resources can also serve requests at the same time.

The gap can run the other way, too. If only 1 job arrived per hour, completions would be 60 minutes apart, but that job would find no line and finish in about 5 minutes. Throughput describes the stream of completions; latency follows one request through the system.

That is why “higher throughput” does not automatically mean “lower latency.” Queueing, concurrency, workload, and the amount of offered work can move the two measurements differently. Before comparing two systems, state:

  1. the work counted as one request;
  2. the system boundary;
  3. the observation interval and workload;
  4. the load conditions; and
  5. how many observations or runs support the claim.

One fast run is evidence about one run. It is not yet a general statement about the system.

Reference and optional depth

The notation and two laws come from Lazowska, Zahorjan, Graham, and Sevcik, Quantitative System Performance, Chapter 3, §§3.2–3.3, pp. 40–46. That chapter is the authoritative course reference; this reading is the introductory route through its key ideas. The opening section draws on the same book's Chapter 1, §1.1, which describes the questions performance analysts answer and the three ways they answer them.

For another plain-language treatment of latency components and the difference between a rated capacity and observed throughput, see Peterson and Davie, Computer Networks: A Systems Approach, §1.5.1. Its examples concern networks, but the measurement distinction applies more broadly.
