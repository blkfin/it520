Stuck on a stage? The online version of this sheet has a hint for each stage.

Stuck on a stage? Each stage below has a hint. It explains what the stage is doing, then works cycle 1 all the way through as an example. Cycles 2 and 3 are yours — the hint tells you the rule to apply and what to watch for, not the answer. Open only the ones you need.

Hint — stage 1, FETCH

What this stage does. The PC holds an address. Fetch goes to that address, copies whatever is sitting there into the IR, and then moves the PC on to the next address. It does all of this before anything knows what the instruction means — fetch is blind, it just collects.

Cycle 1, worked. The PC starts at 0. Address 0 in memory holds LDI 5, so IR holds LDI 5. Then the PC moves on: PC is now 1.

Carry it into cycles 2 and 3. Each cycle starts from the PC you wrote in the row above, not from 0. Notice that the PC has already moved before you get to execute — so during cycle 2 the PC is not pointing at the instruction you are running.

Hint — stage 2, DECODE

What this stage does. The IR now holds something like LDI 5. LDI is not a word — it is a code, and it means nothing until it is looked up. Decode is the lookup, and it produces two things: what operation to perform, and where the result is supposed to go. Both boxes get filled in, every cycle.

Cycle 1, worked. The IR holds LDI 5. Find the LDI n row in the lookup table. Means: load the number 5 into register A. Destination: A.

Carry it into cycles 2 and 3. The destination is not A every time — one of the three instructions sends its result somewhere else, and decode is the only stage that can tell you that. Also: the lookup table has four rows and you only need three. One row is in there to be looked past, so read the code you actually have in the IR.

Hint — stage 3, EXECUTE

What this stage does. Work out the value. That is all. Nothing has been stored yet — the register still holds its old value the whole time execute is running. If you find yourself changing A here, you have run ahead into stage 4.

Cycle 1, worked. LDI 5 loads a number that is carried in the instruction itself, so there is nothing to calculate. Result: 5. A is still unset at this moment.

Carry it into cycles 2 and 3. Cycle 2 needs a value execute cannot invent — it has to come from what A already holds, which is why you write the calculation and then the result. Cycle 3 calculates nothing at all; execute just produces the value that is about to be copied. Producing a value with no arithmetic is still execute doing its job.

Hint — stage 4, WRITE

What this stage does. Put the result from execute into the destination you wrote down in decode. Not the destination you expected — the one you decoded.

Cycle 1, worked. Decode said the destination is A, execute produced 5, so A = 5.

Carry it into cycles 2 and 3. Before you fill in a write box, look left at your own decode box in the same row. If the two disagree, decode is right. And when a value is copied into memory, the register it came from still holds it afterwards — copying is not moving, so nothing gets emptied.

Why could the machine not skip the decode stage on this worksheet?

Model boundary: a real machine stores instructions as numbers, not as short codes like LDI, and its lookup table is built into the hardware rather than printed on a page. We are hiding that encoding so the repeating cycle stays visible.
